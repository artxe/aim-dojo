# calc/

Numeric sens/DPI/mouse-scale math. DOM lives in `controller/`, FOV side effects in `logic.js`, worker tuple format in `worker/`.

## Files
- `calc_sens.js` — per-game in-engine sens + `calc_rad_per_px()` + `lol_sens_to_dpi_scale()` + `calc_sens_r6_file()`. Imports `../math.js` + `../constants.js` ONLY — no `state`
- `calc_dpi.js` — per-game DPI that preserves turning; reads `state.dpi_norm`, takes zero params
- `calc_pubg.js` — `calc_pubg_converted()`, PUBG integer ↔ yaw

## Two layers
`calc_dpi_*` (main thread) read everything from `state` and take ZERO params. `calc_sens_*` / `calc_rad_per_px` are PURE and shared with `worker/calc_worker.js` (which has no `state`), so they MUST stay parameterized (`fov`/`width`/`height` only) — do NOT make them read `state` to "reduce params".

Import boundary is lint-enforced by a file-scoped `no-restricted-syntax` allow-list in `eslint.config.js` (NOT an inline header), keeping the worker tree closed: `calc_worker → calc_sens → math/constants`, `constants.js` imports only `math.js`, `math.js` imports nothing. Same guard on `calc_worker.js` (`../calc/calc_sens.js` + `../constants.js` + `../math.js`) and `bg_worker.js` (`../constants.js` + `../math.js`).

## Non-obvious
- `calc_rad_per_px(fov_deg, width)` → rad/px. The monitor-match point is derived INTERNALLY from FOV geometry: `match = width * (1 - cos(fov/2)) / 2`, the sagitta (arc-height, in px) of the FOV arc with `width` as the circle's diameter — NOT arc-height ÷ diameter (that ratio is just the `(1 - cos(fov/2)) / 2` factor). So the matching distance grows super-linearly with FOV and collapses to 0 (plain linear sens) as FOV → 0. Because `match ∝ width`, `width` cancels in the return and the result is exactly ∝ `1/width` — which is WHY `match` must stay a length (px), not the dimensionless ratio. The return is the mean rad/px over `[0, match]` (a secant slope), slightly below the on-center peak (~3 % at 90°, ~18 % at 120°). It is the hot inner of nearly every sens calc; `on_mousemove` does NOT call it — it reads the cached `state.camera.sens`
- There is NO `match`/DPI parameter (removed with the worker's `dpi_x` field). DPI affects sensitivity ONLY via (a) OS pixels feeding the cached `state.camera.sens`, and (b) the explicit `dpi * sens` factor inside `calc_dpi_*`. The matching point is purely geometric (FOV + width), identical across DPIs
- **Sens is VIEW-INDEPENDENT** — FPP/TPP is render-only. `state.camera.sens` is always plain `calc_rad_per_px(fov, width)` regardless of dimension, and every game match (hipfire/ADS/scope, TPP or FPP) is that plain formula at that view's FOV. The TPP feel is re-created visually by the `state.camera.dist` orbit (`constants.tpp.<game>` × `render_dist_scale`), so parallax exists identically in trainer and game and cancels out of every sens number — yaw-per-count is the whole match. `constants.tpp.*` is therefore renderer-ONLY: tune orbit distance visually without touching sens. Feel-verified three times: pubg TPP-hipfire ↔ ADS both read plain and transition naturally; bdo's old ×2.88 read ~133 at FHD when plain ≈46 was right; mc's old TPP parallax multiplier (×~1.79 at vfov 110) read "way too slow". Removed 2026-07 along with `calc_tpp_rad_per_px`/`calc_sens_fn_tpp`/`calc_sens_mc_tpp`/`calc_pubg_fpp_fov`/`constants.tpp.parallax_distance_scale`. **Do NOT reintroduce a parallax/cross-view multiplier**
- Aspect handling splits three ways — mirror the right one when adding a game:
  - aspect-aware, HORIZONTAL fov at a fixed 4:3 basis (`al`, `cs2`): `convert_deg_across_aspect(hfov, 4/3, width/height)` re-bases to the real aspect
  - aspect-aware, VERTICAL fov (`bdo`, `mc`, `r6`, `rb`): `convert_deg_across_aspect(vfov, height, width)` derives the real-aspect horizontal
  - aspect-independent (`fn`, `ow`, `pubg`, `val`); `sa` is aware but hardcodes 4:3 via `height * 4 / 3` instead of calling the helper
- `convert_deg_across_aspect` doubles as a fixed-ratio ZOOM when both spans are constants. All FOV values, base and zoomed, live in `constants.js`'s `fov.<game>` IIFEs and are computed once at module load: `val`'s 2.5× ADS is `convert_deg_across_aspect(hipfire, 2.5, 1)` (same pattern for `al`/`r6` `xN`), and `ow`'s hero FOVs (`ashe`/`emre`/`freja`/`widow`) use a FIXED `(angle, 9, 16)` — OW's per-hero scope values are VERTICAL in-game, so they are re-based from a 9-unit vertical span to a 16-unit horizontal one to get the horizontal fov `calc_sens_ow` needs; `render`'s `widow` entry is deliberately the RAW unconverted constant because `render[]` already wants vertical-at-16:9. `logic.update_camera_view()` and `calc_worker.js` just read `constants.fov.<game>.<field>`. Constant-span calls are aspect-INDEPENDENT, so they never go stale on resize
- `calc_sens_*` returns raw in-engine sens. `calc_worker.update_game_sens` derives multipliers (`x2`, `x4`, scope) by re-calling at the zoomed FOV and dividing by the hipfire baseline. That zoomed field is usually `convert_deg_across_aspect(base, N, 1)` — NOT a literal `FOV/N`; only `pubg` divides FOV directly (`base/N`), and `cs2` stores literal scope FOVs
- **`fn` has two formulas**: `calc_sens_fn` (tan-ratio) feeds `calc_dpi_fn`; `calc_sens_fn_legacy` (linear fov-ratio) feeds the worker display tuple. Both use the `.005_555` scale — keep them distinct
- `calc_sens_r6_file()` produces the R6 `GameSettings.ini` values AND the displayed card: yaw/pitch fixed at 1 with the 6 dp `MouseSensitivityMultiplierUnit` carrying the whole hipfire sens; 8 ADS scope ints ≤ 200 share a 6 dp `ADSMouseMultiplierUnit` grid-scanned over `[max_ratio/200, max_ratio/100]` for minimum worst-scope error
- Each `calc_sens_*` reads its game's FOV base from `constants.fov.<game>` but hardcodes its own quirky sens-scale multiplier: `al`/`cs2` `.022`, `bdo` `.001_84`, `fn` `.005_555`, `ow` raw rad `.006_6`, `r6` `.005_73`, `rb` `.397_83`, `val` `.07`; `pubg` is log-scale (`base_sens = 50`, `step ≈ 15.0515`). Don't guess — copy from the game's actual config
- `lol_sens_to_dpi_scale()` is LOL-only — piecewise-linear over 11 anchors (`.031_25 … 3.5`). LOL has no in-game sens, so the DPI normalizer rescales DPI instead
- PUBG `game.pubg_fov` is `80` or `103`. `80` → the trainer's fixed-FOV TPP hipfire, `103` → FPP hipfire at 103°. Only the Normal/hipfire calc follows the preset, because `FpsCameraFov` does not change the fixed ADS/scope FOVs. The INI rewrite writes the selected `FpsCameraFov`, and `calc_dpi_pubg()` applies the same FOV to both yaw scaling and monitor matching. The old `calc_pubg_fpp_fov()` bisection double-corrected for parallax that cancels — don't resurrect it

## When you change…
- A sens formula: also verify the matching `logic.update_camera_view()` branch — the FOV the renderer uses must match the FOV the sens calc assumes, or mouse and target scale diverge
- `calc_rad_per_px`: readers go through the `state.camera.sens` cache, so formula changes propagate automatically (root `CLAUDE.md:Change map → target/camera/impact math`)
- PUBG math: `calc_pubg.js` + `calc_sens_pubg()` + the PUBG INI rewrite in `controller/game_sens.js` — all three
- Add a sens game: root `CLAUDE.md:Change map`
