# controller/

UI events + HUD. May read/write `state`, call `logic.js`, post worker messages, update DOM. Game rules stay in `game_mode/`.

## Files
- `window.js` — keyboard/mouse/pointer-lock/resize/hash. Side-effect imports `cpi_norm`, `game_sens`, `menu` (boots them); named-imports `tutorial` (boots it too). Exports `on_resize()`, also bound to `visualViewport`'s `resize` for mobile URL-bar changes. `hashchange` → `setting.js:sync_setting_hash`; the first `keydown`/`mousedown`/`touchend` (three `{once:true}` listeners) calls `renderer_bg.js:enable_bg_audio` to satisfy autoplay
- `dom.js` — 191 centralized DOM refs + `reset_hud_labels`, `send_toast`, `set_attr_if_changed`, `set_hud_labels`, `set_mode_score`, `set_text_if_changed`. Add new refs here first. **The three `#hud-score` labels are per-MODE**, because each mode's number is a different measurement: `set_hud_labels(run_score, accuracy, crit_rate)` is called from every `init()` (`Bit/s`/`°/s`/`Cleared/s`/`Px/s`, and `On Target`/`On Text` where a whole stroke or a held crosshair is what counts) and `reset_hud_labels()` from every `dispose()`, so the menu and the tour's HUD preview always show the `HUD_LABEL` defaults instead of the last mode's. `set_mode_score(score_el, clear_btn, score)` is the SINGLE writer of a mode's record display — it also sets `clear_btn.disabled = !score`, so a 0-score mode's Clear button is dead
- `hud.js` — `update_hud(mode)` takes the ALREADY-resolved `GameMode` from `logic.on_frame()`, so it never imports `game_mode/index.js`. Calls `mode.update_hud()`, then writes fps (the frame COUNT over the last `constants.hud.fps_interval_ms`, held between windows — see the root note) + elapsed timer, the `2D` / `<dimension> <fov>°` readout, and the `error: ±N%` line (`state.camera.sens_error` as a 2 dp percent through `format_error()` — already derived by `update_camera_projection()`, so the HUD does no sens math; the status box is `h=3lh` for its three lines). It was `error-h` beside an `error-v` line for the first days of 2026-09; the vertical readout went with the per-game CPI ratio (root `CLAUDE.md:camera.sens_error`). `update_hud` is its ONLY export — the `set_controls(name, mode)` half died with the `#controls` panel (below), taking `constants.mode.*.guide` with it
- `menu.js` — the 4 mode buttons; passes the mode name to `start_game(mode)`. The settings button is bound in `setting.js`, NOT here
- `setting.js` — bg/crosshair/audio/copy/clear-score/hash sync; exports `close_setting_view()`, `init_bg()`, `on_click_modal_backdrop()`, `open_setting_view(section?)`, `parse_color()`, `sync_setting_hash()`. The two view functions are exported FOR `tutorial.js` — `open_setting_view()` with no argument is the Setting button's own path (hash `#setting`, scrolled to the top). It opens with `close_game_sens_list()`, so the Setting button, a `#setting-*` deep link and the tour's settings steps all fold the sens list the same way (this file's ONE import from `game_sens.js`)
- `tutorial.js` — the guided tour behind the menu's Tutorial button; exports `is_tutorial_active()`, `layout_tutorial()`, `step_tutorial(step)`, `stop_tutorial()`
- `game_sens.js` — game resolution inputs, active sens game, settings-file rewrite, the per-game `Trainer ADS` selectors, the 73 sens DOM cells (one `set_text_if_changed` each, so the count is checkable). Exports `init_game_sens()` + `sync_game_resolution()` (the second is called by `logic.start_game()`, making this one of the three controller modules `logic.js` imports: `dom`, `hud`, `game_sens`)
- `cpi_norm.js` — CPI normalizer inputs/result

## Background settings (setting.js)
**Commit-on-Save, NO live preview.** `bg_snapshot` + localStorage = committed; `state.bg` = currently DISPLAYED. Both are a `BgSpec` (global, `private.d.ts`).
- `staged_bg()` reads the widgets · `show_bg(spec)` applies playback + sets `state.bg` (no commit; `bg_shown_video` / `bg_iframe_el.src` no-reload guards + `bg_apply_token` for out-of-order awaits) · `commit_bg(spec)` writes `bg_snapshot` + localStorage
- Selecting a radio/option changes NOTHING visible — it only stages. **Activate** = `show_bg(staged_bg())` + `bg_el[activate]`, the only preview path, layered OVER the still-open settings (`index.html` z-order: settings `z=2` < `#modal-backdrop` `z=3` < `#bg[activate]` `z=4`). **Dismiss** → `show_bg(bg_snapshot)`. **Save** = `show_bg(staged)` → `commit_bg(staged)` (youtube also activates the card); Save does NOT close settings. **Close settings** → `reset_bg_widgets()`
- Boot (`init_bg`): `set_bg_widgets` + `show_bg` under `bg_suppress`; a committed youtube auto-activates because autoplay is blocked
- Widgets: three `name="bg-type"` radios (`video` | `youtube` | `none`) + hidden `#bg-type`; `:checked` CSS swaps `#bg-link-wrap` against `#bg-video-select-wrap`, and `none` checked shows neither. The `video` radio covers BOTH `default` and uploaded — `x-select#bg-video-select` decides which. Static rows use `data-value`, uploaded rows add `data-removable`, upload is `data-action="upload"`; `bg_video_option()` builds the `<li>` incl. delete + long-name (`> 18`) marquee. Collapsed width matches `#bg-link`'s `w=25ch`
- Upload persists to IndexedDB first, then re-stages via `render_bg_options(id)` ONLY if radio + selector stayed unchanged during the await. Delete = `selectremove`; deleting the committed video commits + shows `default`
- **`none` is the focus option: it turns the background OFF, it is not a fourth source.** `staged_bg()` returns it carrying the snapshot's `video_id`/`youtube_link` untouched, so picking None and Saving never forgets which video or link the user had; that is also why `set_bg_widgets` re-selects `spec.video_id` for every type but `youtube`, so the Video radio comes back holding the upload rather than falling to `default`. `show_bg`'s `none` arm runs `set_bg_upload_video(null)` like the default arm, and `data-show=none` matches none of the three `:not([data-show=…])` rules, so canvas, video and iframe hide at once. `renderer_bg.js` needs NO branch: `update_bg_video()`'s two `else`s already pause both elements for any non-`video`/non-`default` type. **Hiding the three children is not enough, because the layers BEHIND `#bg` are the default clip too** — `#bg-preview` is a still strip of it and `body`'s own background tile is a 16×27 LQIP of its first frame, so None fell through to a blurry upscale of the very video it was meant to turn off. `#bg` therefore paints itself opaque (`[data-show=none]/bg=#000`), covering `#bg-preview`, the transparent `#modal-backdrop` and the `body` tile in one stroke. **The colour is on `#bg` and not on a child so that the run and the menu look IDENTICAL** — every `[locked]`/`[rest]` filter in `body`'s class string targets `#bg-preview` or `#bg>canvas|iframe|video`, never `#bg` itself, so no dim, blur or screensaver state can move it off black. `#bg-preview` is ALSO hidden (`body`'s `:has(#bg[data-show=none])_#bg-preview/none`) for the one case the black plate misses: `#bg[activate]` scales `#bg` to `.8` and the preview's still frame would show around the edges. That rule has to hang off `body:has()`, since `#bg-preview` PRECEDES `#bg` and no combinator reaches backwards
- `#bg[data-show=default|none|video|youtube]` picks which child shows (`show_bg` sets it). `show_bg` keeps the youtube iframe `src` loaded while youtube is still committed so Activate-another → cancel doesn't reload it; `commit_bg` clears the `src` when committing a non-youtube type

## Tutorial tour (tutorial.js)
One ordered `steps` array of `TutorialStep` (`{ el, game?, keys, text }`, `private.d.ts`) drives everything — **44 steps** = 19 literal entries + a 25-step generated sens stretch (12 cards + 13 extras): 2 menu/card steps, the monitor row, the stretch, 4 mode steps, two in-run HUD steps, the Setting button, its 8 sections, and a closing step. Order is the tour, so it is the ONE array in the repo deliberately not alphabetized; the stretch is the one generated run (`...sens_games.flatMap(sens_step)`).

### Structure
- **A card's interactive controls are `extras` ON the card, never separate entries in `steps`.** `sens_cards[game].extras` is an optional `{ el, text }[]` and `sens_step` returns `[card, ...extras]`, so `flatMap` lands each control DIRECTLY AFTER its owning card — LoL card, LoL sens field, next game — instead of stranding all thirteen behind the whole 12-card walk. The thirteen are the eight `<game>_ads_scope_select`s plus `lol_sens_input`, `mc_file_el`, `pubg_fov_select`, `pubg_file_el`, `r6_file_el`. **An `extra` deliberately has no `game` of its own**: each lives in its card's `div`, which `[open]>li:not([active])>div/none` hides for every card but the active one, so a control step arriving without `game` would spotlight a `display: none` box and measure 0×0 at the origin — `sens_step` stamping the parent card's `game` makes that unrepresentable rather than merely documented
- `monitor_el` is the one control needing no `game` (it sits in `main` above the `ul`). **It comes BEFORE the stretch, not after** — every card is computed for that resolution, so explaining 17 steps of numbers first and only then revealing what they were computed against had the tour backwards. It still comes after the list step, because its text opens by referring to "the cards below"
- **`sens_cards` is a `Record<GameSensName, …>`, not a Partial** — tsc fails until a newly added sens game has both its `li` ref and its player-facing quirk written. It carries the element so the game→`li` mapping lives in ONE place instead of being re-spelled beside `game_sens.js:active_game_sens()`. `sens_games` is its `Object.keys()` (one cast), so key order IS tour order and matches the DOM list. Notes cover what the player actually hits (SA's RMB click-through zoom stages, SA/`bdo` never zoom-correcting so the HUD sens line reads far off zero, MC's slider being unable to express the value), NOT the FOV-axis theory — the card labels (`Hipfire(110)`, `Hipfire(16:9)`, `Hipfire(85, 1024x768)`) carry the basis already

### The tour drives the sens card
- `show_step()` opens with `set_active_game_sens(game || tour_game)` plus `game_sens_list_el.toggleAttribute("open", el == game_sens_list_el)`, both on EVERY step. A step carrying `game` switches the card to it; a step without one falls back to `tour_game` — the user's OWN game as it stood when the tour opened, snapshotted in `on_click_tutorial()` (not at module load; the user may have switched since boot). There is deliberately no "leaving the game block" detection: every non-game step re-asserts the snapshot, so Next, Prev, a shade click, Skip, Escape and Done all restore for free. `stop_tutorial()` repeats the pair only because it does not go through `show_step()`
- **`[open]` is derived from the STEP, never snapshotted.** The list is folded for every step but the one spotlighting `game_sens_list_el` itself. So a mid-tour click that opens the list cannot leave it hanging, and `stop_tutorial()` ends on `close_game_sens_list()` — the tour simply CLOSES the list, it never restores an earlier fold state
- **A game step highlights its own `li`, not the `ul`, and the list stays COLLAPSED.** Collapsed, `li:not([active])/none` leaves the `ul` wrapping exactly one card, so the spotlight sits on the card the step is about and the switch reads as that card's contents changing under the highlight. Force-`[open]`ing it (tried once) also meant pressing Tutorial UNFOLDED a list the user had left closed. `set_active_game_sens()` deliberately does NOT touch `[open]`. The `extras` steps work collapsed: `[open]>li:not([active])>div/none` hides a card's detail block only while the list is unfolded
- **`[open]` is set in `game_sens.js` and cleared from four places.** `change_active_game_sens()` (user picked a game) is the only opener; `close_game_sens_list()` is the single clearer, and **everything that takes the screen away from the list calls it: `logic.start_game()`, `setting.js:open_setting_view()`, `tutorial.js:stop_tutorial()`**. Picking a different game is NOT required to close it. `start_game()` calls it BEFORE its `await`s so the list is closed before `[locked]` lands — closing it in CSS instead left the attribute set and the list sprang back open when the run ended. During a run only the resolution row and the ACTIVE game name show: the closed list hides the other 11 through `li:not([active])/none`, and `body`'s `[locked]_#game-sens-list_li>div/none` hides the surviving card's detail block
- **`game_sens.js:set_active_game_sens(name)` is the tour's entry point**: `change_active_game_sens()` minus the `localStorage` write and the `[open]` collapse, so **the tour can never persist a game change**. `change_active_game_sens()` delegates to it and adds the persist. Its `name == state.game.sens` early return makes the per-step call idempotent (most steps re-assert the same game) — remove it and every step churns `[active]`, re-measuring a mid-transition card. `update_game_sens()` computes all 73 cells for ALL games regardless, so switching needs no recompute; `[active]` only decides which card is VISIBLE

### Escaping `#game-sens-list`'s clip
- **`#game-sens-list` scrolls VERTICALLY ONLY** (`max-height=calc(100dvh_-_48px) ox=clip oy=auto scrollbar-gutter=stable`, `48px` = `main`'s `t=8` + the monitor row + slack). `ox=clip` is load-bearing: CSS forbids `overflow-x: visible` beside a non-visible `overflow-y` and silently computes it to `auto`, so without it the reserved gutter alone raises a horizontal scrollbar. `clip` is the only value keeping the axis unscrollable; `scrollbar-gutter=stable` keeps it from clipping anything real, since the gutter is reserved at all times. The `calc()` spaces are hand-written as `_-_` — click-css v1.1.0 dropped the pass that inserted them, so a bare `calc(100dvh-48px)` emits verbatim, the declaration is dropped as invalid, and the list silently loses its cap
- **Two out-of-flow children have to escape that clip: the file boxes' `:hover:after` path tooltip and the `Trainer ADS` dropdown.** A scroll container always clips to its scrollport, so `overflow-clip-margin` does nothing and wrapping the tooltip (`w=16ch;ws=normal`) is out — the label must stay on ONE line. Both escape with `position: fixed` (containing block is the viewport; no ancestor here has a transform/filter to trap it) plus `anchor()`, which keeps them pinned as the list scrolls
  - Tooltip geometry: `fixed;left=anchor(left);ml=12;mt=12;t=anchor(top)` on the same `:hover:after` class as the appearance — TOP and LEFT edges plus a matching positive inset, so it reads as a plain `left: 12; top: 12` INSIDE the box. The two margins are equal on purpose and move together. Two ways to get it wrong, both shipped once: `bottom=anchor(top)` pins the tooltip's BOTTOM to the box's top and lifts it clear of the box, and a NEGATIVE `mt` hangs it across the top edge
  - Dropdown: `top: anchor(bottom)`/`left: anchor(left)` + `position-try-fallbacks: flip-block` so it opens upward near the viewport bottom. The `Trainer ADS` row is the LAST line of every card, so an `absolute` dropdown was cut off on every card
  - **Both rules live in `index.html`'s `<style>` block, not in click-css**, because click-css rewrites any `--ident` after `:`/space/comma into `var(--ident)` (`L=/\([^)]*\)|[: ,]--[^ ;,)]+|(?<=[: ,])~(?=[-.\d])/g`, the rule that makes `c=--active` work), so `anchor-name: --mc-file` would come out as `var(--mc-file)`. **The anchor is named EXPLICITLY** — `#<id> { anchor-name: --<id> }` + `#<id>::after { position-anchor: --<id> }` for `mc-file`/`pubg-file`/`r6-file`; only `position-anchor` needs to be per-id for the dropdown, whose shared half is one `[id$="-ads-scope"] > [data-select-options]` rule. Relying on the implicit anchor FAILED in the browser: with `anchor()` unresolved, `left` computes to `auto`, the `fixed` box falls back to its static position, and the fieldset's `jc=center` centred a `ws=nowrap` tooltip far wider than the card, hanging it off the LEFT edge. If you see that centring again, this block went missing. Do NOT put `absolute`/`l=`/`t=` back on any of those classes — it re-parents them into the clip
- `anchor(top)`/`anchor(bottom)` survive the unit pass only because click-css v1.1.0 skips parenthesised values (v1.0.0 would not have)

### Dim, blur, hole
- **The dim and the blur are TWO layers, and they have to be.** `#tutorial-spotlight` is sized to the target's rect + `PAD` and paints the whole dim as its own `box-shadow` spread (`bsd=0_0_0_100vmax_rgba(0,0,0,.72)`) — no four-panel cutout. **A box-shadow cannot carry a `backdrop-filter`** (the filter applies to an element's own border-box backdrop, never to its shadow), so the blur is a separate full-screen plate with a hole punched in it: `#tutorial-shade`, `bf=blur(3px)` + a `clip-path` written by `layout_tutorial()`. The shade sits BEFORE the spotlight so the shadow dims on top of the blur
- **The hole is `path(evenodd, "…Z …Z")`, NOT `polygon(evenodd, …)`.** `polygon()` is ONE auto-closed path with no subpaths, so an outer ring followed by an inner ring closes the last hole corner straight back to the first outer point and the outbound/return edges enclose a real triangle — the shade renders punched through from the top-left corner to the highlight. `path()` gives two genuinely `Z`-closed subpaths and no connecting slit (a degenerate out-and-back slit cancels in the fill rule but still rasterizes a hairline). Its `M H V H Z M H V H Z` command list is constant, which lets `tr=clip-path_.15s_ease` interpolate the hole in step with the spotlight's own `.15s`; `path()` coordinates are plain px, hence `innerWidth`/`innerHeight` for the outer rect. `el: null` sets `clip-path: none`, blurring the whole screen — what the intro and closing steps want — and `[blank]` drops the tip's border so the 0×0 box keeps the shade full-screen while the tip centres
- **An open `x-select` dropdown is unioned INTO the hole**, or it sits on the blurred, dimmed side: `layout_tutorial()` resolves `open_select` as `el` itself when `el.matches("x-select[open]")` and otherwise as `el.querySelector("x-select[open]")`, then widens the rect by that select's `:scope > [data-select-options]`. **BOTH arms are load-bearing** — the sens-card steps spotlight the select directly, the settings steps spotlight the whole `fieldset` with the select nested inside. The query must be `x-select[open]`, never a bare `[data-select-options]`: `game_sens_list_el` also carries `[open]`, so a loose query would find the PUBG card's dropdown and stretch the hole to it
- **Layering: `#tutorial-view` (`z=5`, over `#setting-view`'s `z=2` and `#bg[activate]`'s `z=4`) inherits `body`'s `pe=none` and receives nothing.** `#tutorial-shade` is `pe=auto` + `cs=pointer` and is the only thing advancing the tour by click (`on_click_shade`, `ev.target == tutorial_shade_el`); a `clip-path`-clipped region is not hit-testable, so the hole falls through to the real UI. `#tutorial-spotlight` is `pe=none` PERMANENTLY so it never plugs the hole it draws — hover is not optional, the file boxes' path tooltip is a `:hover:after`. `#tutorial-tip` needs its explicit `pe=auto` or Prev/Next/Skip go dead. **Clicking the hole does NOT advance the tour** — an earlier build advanced on any blocked click and it fought every attempt to use the highlighted control

### Input while the tour is up
- **Mouse input is allowed everywhere except a short blocklist.** `window.js:block_tutorial_click` is registered three times — capture-phase `mousedown`, `mouseup` and `click` — and `preventDefault()`s + `stopPropagation()`s anything inside `activate_bg_btn`, `menu_el` or `save_bg_btn`, plus any element matching `#game-sens-list li > b`. `menu_el` covers three hazards in one containment test: the 4 mode buttons, `setting_btn`, and `tutorial_btn` (restarting the tour from step 1 mid-run). The other two are ONE hazard behind two doors — both set `bg_el[activate]`, raising the preview to `z=4` over the very settings panel the tour points at, so `save_bg_btn` is blocked alongside `activate_bg_btn` even though it only activates for `type == "youtube"`. The fourth entry is a `matches()` on the card TITLES, not a `contains()` on `game_sens_list_el`: pressing a title runs `change_active_game_sens()`, the ONE path that unfolds the list or switches+PERSISTS a game. **Everything else in a card stays live** — the `Trainer ADS` selectors, the file boxes and the `lol` sens input each get their own spotlighted step and must be operable there. **Capture is REQUIRED** (the menu binds `click` but the cards bind `mouseup`, so a bubble-phase guard runs too late) and **all THREE events, not just `click`** — `on_mousedown` sets `state.input.mb_right` unconditionally while `on_mouseup` (a `document` BUBBLE listener, downstream of the capture stop) clears it, so blocking only the release would strand the flag true until the next blur. Known and accepted: `#setting-clear-score`'s buttons really do wipe a best score
- **The cursor NEVER follows the block — every blocked control keeps the pointer it has off-tour.** A tour-only arrow reads as the UI having broken, and those buttons are still the real controls the tour is standing in front of. Do not add a `cs=default` override for blocked buttons, and do not add `#game-sens-list_li>b` to any such list. The inverse IS wanted: the card TITLES (`li > b`) and the three file boxes carry real handlers but inherited the default arrow, so they carry an explicit `cs=pointer` — on the `b` and the `fieldset`, not the `li`, since a click inside the card's detail `div` is deliberately ignored by `change_active_game_sens()`
- **Scrolling is blocked** by a `{ passive: false }` `wheel` listener (`on_wheel`), while a CAPTURING `scroll` → `layout_tutorial` listener stays as the correction path for scrolls the wheel block cannot reach — chiefly the browser scrolling an input into view when you click one inside the hole. Capture is required because `scroll` does not bubble out of `#game-sens-list`/`#setting-scroll`. A document `click` → `layout_tutorial` (bubble, so it lands after the real handler toggled `[open]` or opened a dropdown) re-measures too. Both cost nothing off-tour, since `layout_tutorial`'s first line is the `is_tutorial_active()` guard
- The snap-back is `scrollIntoView({ block: "nearest" })` doing double duty: the same call that brings a target into view on a step change is a no-op while it is fully visible. `layout_tutorial()` runs it BEFORE measuring — nothing in the page sets `scroll-behavior: smooth`, so the scroll lands synchronously and the `getBoundingClientRect()` right after is the settled rect. It must be the `ul` and not `main` that scrolls: `body` sets `pe=none` globally and only `#monitor`/`#game-sens-list` re-enable it, and a `pointer-events: none` box is not hit-testable, so a wheel over `main` would never scroll it
- `window.js` owns every input path in: Escape → `stop_tutorial()` (checked BEFORE `is_modal_active()`, so it also closes the settings view the tour opened), ←/→ → `step_tutorial(∓1)`, and while the tour is up `on_keydown` returns before touching `state.input`. `on_resize()` ends with `layout_tutorial()` (a no-op when inactive) so the highlight follows a window resize
- **The screensaver is suppressed while the tour is up** — `reset_screen_saver_timer()` arms only when `!mode && !is_tutorial_active()`. Without it `body[rest]` hides the very UI being highlighted after 5 s of reading. `on_click_tutorial()` also clears the timer already pending from its own mousedown

### Tip, HUD preview, wording
- Tip placement is below → above → right → left, each fallback tried only when the previous overflows, then a final `clamp` to the viewport. It measures `offsetWidth`/`offsetHeight`, so **the tip must never transition its SIZE** — a transitioning width measures mid-animation and mis-places the box. **Its POSITION is free and is deliberately animated**: `tr=left_.15s_ease,top_.15s_ease` matches the spotlight beat for beat so the two travel together instead of the highlight gliding while the text teleports. That property list is the whole guard — never widen it to a bare `tr=.15s_ease` (`transition: all`), which sweeps `width`/`height` back in. Nothing reads the tip's own `left`/`top` (placement comes from the TARGET's rect and the tip's size), so animating them cannot feed back into `place_tip()`
- The spotlight's `tr=.15s_ease` IS `transition: all` on `left`/`top`/`width`/`height` — the move that shows WHERE the highlight went — and nothing measures it either. **`index.html` has NO `prefers-reduced-motion` block**: this audience strips Windows for latency, `SPI_GETCLIENTAREAANIMATION = false` makes Chrome report `reduce`, and honouring it meant most players saw the highlight teleport. Headless Chrome also always reports `reduce`, so anything gated on that query can never be confirmed by a screenshot pass
- **The two HUD steps spotlight the REAL readouts, so the tour has to turn them on and fill them.** `#hud-score` (top-centre: the mode's own score label · `Accuracy` · `Critical` · `Level`, defaults `Score`/`Accuracy`/`Critical`) and `#hud-status` (top-right fps/elapsed, view + fov, `error: ±N%`) are ids on the INNER absolute boxes, NOT on the `[hud]` wrappers: a wrapper is `fixed` with no width and shrink-wraps around an absolutely-positioned child, so its rect is a 0-wide sliver. `show_hud_preview(on)` — derived per step as `el == hud_score_el || el == hud_status_el`, never a flag on the step — toggles `#tutorial-view[hud-preview]`, which `body`'s `:has(#tutorial-view[hud-preview])_[hud]/block` reads to beat the standing `:not([locked])_[hud]/none` (the `:has()` carries an id, so it outranks it at any source order — and the attribute is `hud-preview`, never `hud`, or that same `none` rule would hide `#tutorial-view` itself). It also WRITES `HUD_PREVIEW`, because the four score spans are `:not([value])/none` and an empty score block measures 0×0. The numbers are one consistent run (30 shots, 26 hits, 9 crits ⇒ `86.67%`, `34.62%`); the score pair is a plausible throughput, not a derivation, because the score is now a bit/s MEASUREMENT over a 30 s window rather than a formula over those counts — and the score step's text says they are an example. Every other step calls it with `false` — hence `set_*_if_changed` rather than blind writes — and `stop_tutorial()` repeats the call so the attribute cannot leak the HUD onto the menu
- **`Skip` leaves the TOUR, `Exit` leaves a RUN — one word per action, never crossed.** The first step's `keys` is BUILT from `NEXT_LABEL`/`PREV_LABEL`/`SKIP_LABEL` rather than retyped, because it names the three buttons sitting right under it and a renamed button has to drag its own hint along. Escape and the Skip button are the same call, so they must never carry different words. Every other `Esc: Exit` in the file (the `mode_keys()` template, the closing step) describes IN-RUN controls, where Escape really does end a run
- A step whose `el` is inside `setting_view_el` opens the settings modal through `open_setting_view(el)` (hash + `scrollIntoView`, still `replaceState`, so the tour never pollutes Back); leaving those steps — and `stop_tutorial()` — closes it again. Membership is derived with `setting_view_el.contains(el)`, so no per-step flag
- **The tour is the ONLY place the controls are explained** — the in-game `#controls` panel was deleted once it existed. Its RMB rule survives in `mode_keys(name, fire)`, which derives that half from `game_mode[name].update_dimension` instead of typing it per mode (with a static `(Shoot in League)` aside, because the pair is built at module load and cannot follow the game); only the Tap/Hold and the trailing `Esc: Exit` + Space hint are copy. A new mode with no step is a mode nothing documents. The tour also carries what a player only meets mid-run: the two HUD steps, and that the error line reads the in-game sensitivity against the recommended one, so it goes large wherever a game's own fields cannot cover the FOV. **Do not re-add a claim that the run repeats the controls on screen** — that sentence outlived `#controls` and shipped as a pointer to a deleted panel

## Settings deep link (setting.js)
The location hash IS the modal's open state, synced both ways with `history.replaceState` (never `pushState`, so settings never pollute Back). `sync_setting_hash()` runs on boot and every `hashchange`: `#setting` opens at the top, `#setting-<section>` opens scrolled to that `fieldset[id^="setting-"]`, anything else closes + `reset_bg_widgets()`. Going the other way, `change`/`click`/`focusin` inside the modal rewrite the hash to the target's `closest("fieldset[id^='setting-']")`, and so does `mouseenter` on a section — but the HOVER path alone is gated by `setting_mouse_moved` (set by a `mousemove` that actually moved, cleared by `scroll_setting_hash_target()`), so the programmatic `scrollIntoView` from a deep link can't instantly overwrite the hash the user arrived with.

## game_sens.js specifics
- Recommend CPI lives HERE, not in `cpi_norm.js`: `#cpi-x` is an input bound in this file's init block, `#cpi-y` a derived span, both written by `update_cpi_display()` — only a WIDTH change moves them (auto-X), so `on_change_monitor_height` and `on_change_pubg_fov` do not call it. **CPI is an INTEGER everywhere** — `state.cpi_norm.x` stores exactly the whole number typed (`round`ed, never rescaled), the input carries no `decimals` attr so arrows step 1, and `y` is `round(x * ratio)`, never user-set
- **The Y/X ratio is a FIXED `constants.cpi.ratio` = 1.5, by decision (2026-09-05) — not typed, not computed, independent of game, FOV and aspect.** √2 is a plane's Y/X; most games expose ONE sensitivity field matched horizontally, which leaves the vertical that much slow against its own FOV basis, and 1.5 is the flat number chosen to carry that on the mouse (it sits 0.41 % under the 103° @16:9 optimum, 1.50624 = √2 × `calc_vh_ratio`). For one week of 2026-09 the ratio was `√2 × calc_vh_ratio` at a `Y/X Game` selector's hipfire (`val`/`ow` 1.50624, `cs2` 1.528, `pubg`-80 1.431, `r6` 1.693, `rb` 2.192 @FHD); that selector, `state.cpi_norm.target`, `#cpi-ratio` and `calc_cpi_ratio()` are all gone — do not bring a per-game ratio back without deciding it explicitly. Nothing on the vertical axis moves with FOV any more: the five games with a vertical field of their own print it EQUAL to the horizontal one (`calc/CLAUDE.md:No vertical fields`), no `calc/` function takes a `cpi_v`, and the trainer's pitch runs at the plain `sens` — the HUD's `error-v` line went with the ratio too
- `state.cpi_norm.x = 0` (nothing stored) means AUTO: `current_cpi()` falls back to `round(constants.cpi.x * width / 1_920)`, the only place resolution still scales the recommendation — a user-set CPI is a physical mouse setting and must NOT move with resolution. Clearing the field + Enter re-enters auto. `current_cpi().x` also feeds every eDPI cell, so the handler re-runs `update_game_sens()`
- **Game resolution is `#monitor-width` × `#monitor-height`, two free integer inputs — NOT a preset list.** No `MonitorResolution` enum, no `state.game.resolution`; `state.js` seeds `game.width`/`game.height` from `round(screen.width/height * devicePixelRatio)` with localStorage overriding. Free numbers because presets could never cover what matters — ultrawide, 16:10, and CS2/Valorant stretched res (1280x960 on a 16:9 panel), a DIFFERENT aspect from the panel that only the player knows. **These drive the CARD only**; the trainer's own feel is fullscreen and reads the real `state.camera.width/height`
- **Starting a run overwrites them.** `logic.start_game()` calls `sync_game_resolution()` once lock + fullscreen are granted: recompute, persist, refill both inputs, then re-run auto-CPI + normalizer + `update_game_sens()` — early-returning when nothing moved (the usual case). So a hand-typed resolution is for card-matching a machine you are NOT on and lasts only until the next run; the card can never quote a resolution the trainer is not rendering at. It reads `screen.*`, NOT `state.camera.width/height`, because the camera is still WINDOWED size until the fullscreen `resize` lands. Trade-off: browser zoom inflates `screen.* × devicePixelRatio`, exactly as it does for `state.js`'s seed
- **Recommend's X/Y pair is usable on ANY mouse, not just dual-axis ones.** `rawaccel.net` — linked right under it — is a kernel-level driver that applies the 1.5 Y/X ratio itself. The tour says so; do not re-narrow that line to "mice with separate axes"
- **CPI vs DPI is a real distinction, not a spelling choice.** Everything set on the mouse is counts — `#cpi-x`/`#cpi-y`, `#cpi-norm-cpi`, `state.cpi_norm`, `constants.cpi`. `lol`'s cell is the ONE that stays `DPI` (`#lol-dpi`): it is `x * cpi_scale, y * cpi_scale`, i.e. counts AFTER the in-game/OS multiplier, and LOL is cursor-driven so the result really is screen dots per inch. FPS games spend counts on rotation, never dots
- eDPI is shown ONLY for the four games whose communities quote it — `al`, `cs2`, `ow`, `val` (`ow`'s is the `x, y` pair, the rest a single number). `fn` (quotes `%` + CPI) and `rb` deliberately have none. `eDPI` keeps its spelling — fixed community term, not a units claim
- **The LOL card's `Windows 11` / `Windows 10` rows map `state.game.cpi_scale` BACK to a pointer-speed notch**, because that multiplier is what the OS slider sets and the player must find the notch by eye. `format_win_sens(cpi_scale, points)` walks the table and prints the exact notch on a hit (`EPS` compare), a `4-5` range between two, `<1` below the first, `>N` past the last. **The two tables genuinely differ** — Win10 has 11 notches and jumps `1/16` straight to `2/8`, Win11 has 20 (eighths to `1`, then quarters) — so both rows exist and neither derives from the other. They live in `game_sens.js`, not `constants.sens`: OS pointer-speed notches, not a game's engine curve
- **`Trainer ADS:` is the last row of eight cards** (`al`, `cs2`, `fn`, `ow`, `pubg`, `r6`, `rb`, `val`) — an `x-select#<game>-ads-scope` whose `data-value`s are the keys of `constants.fov.<game>.ads` and whose `data-label`s keep the collapsed button short while the open list spells the weapon group out (`Spectre` / `Ares/Odin/Spectre/Stinger`). It lives on the CARD, not in Settings, for the same reason `pubg_fov_select` does: it is per-game and you pick it while looking at the scope rows it chooses between. `bdo`/`sa` (one forced chain) and `lol`/`mc` (no zoom) get no selector
  - Each has its own `on_change_<game>_ads_scope` — eight near-identical handlers rather than one generic, because `state.game.ads_scope` is eight DIFFERENTLY-typed keys and a `Record<GameSensName, string>` would let `"widow"` be assigned to `al`. They persist to `game.ads_scope.<game>` and call `update_game_sens()`
  - **It is trainer-only: NO card cell depends on the selection.** All eight recomputes are no-ops that `set_text_if_changed` swallows — kept because the next selector-driven cell should not have to remember to add one back, at 0.03 ms. Cards already print a value per scope, so the selection just says which row you are practising; the three shared-field games print the one row their game lets them type, pinned to `ads_ref` (`calc/CLAUDE.md`)
  - **The options are GUNS wherever the game's own sensitivity field is per-gun** (`cs2` AUG/SG556 · Automatic/SSG08 · AWP, `rb`, `val`), heroes for `ow`, the two field names for `fn` each at both of ITS FOVs (`Targeting` → `ADS(80)`/`ADS(65)`, `Scope` → `Scoped(40)`/`Scoped(15)`), and magnifications only for `al`/`pubg`/`r6`, whose games really do expose one box per scope
  - `main.js` seeds all eight `.value`s at boot. `component/select.js`'s setter is SILENT, so that seeding fires no `change` and cannot re-persist
- R6: display AND file both come from `calc/calc_sens.js:calc_sens_r6_file()`, so the card shows the exact INI values, PUBG-style
- **SA's two TRG rows are ENTIRELY static markup.** SA exposes no zoom-sens field (engine hardcodes `x0.25` at stage 1, `x0.15` at stage 2) and the multipliers don't move with resolution or aspect, so there is nothing to compute. The `(20.77)`/`(6.99)` are scope FOVs on SA's own 4:3-horizontal basis — same basis as the `85` in the `Hipfire(85, 1024x768)` label — derived from `constants.fov.sa.hipfire` as `convert_deg_across_aspect(hipfire, 5, 1)` / `(hipfire, 15, 1)`, so changing `hipfire` means retyping all three numbers. RMB is a 3-way cycle on `state.input.ads_stage`; there is no per-stage selector
- Locals feeding more than one cell: `cs2_40` fills `Auto1` + `AWP1`, and `rb_ads`/`rb_rifle_exact` fill the `While Aiming` + `While Scoped` pairs. The `rb` block reads its settable values (`Sensitivity`, `Horizontal`, `Vertical`, `While Aiming`, the Roblox hipfire) off `calc_sens_rb_fields()` (`calc/CLAUDE.md:rb`) and derives only the six per-weapon UNsnapped reference rows (`rb_*_exact`, from `effective`) itself; they are labelled by FOV GROUP (`Assault Rifle/Sniper(45)` … `Minigun(112.5)`), not by individual gun. Read the write block, not just the calc block, before renaming one
- MC card shows `<in-game %>%, <options.txt value>` — percent at 2 dp (`round_to(file * 200, 2)`), deliberately NOT the integer MC labels. **MC's in-game slider is unusable as an input path**, so matching its label is pointless:
  - the label is `(int)(mouseSensitivity * 200)`, a FLOOR ⇒ many-to-one. `100%` means `mouseSensitivity ∈ [0.5, 0.505)`, not `0.5`
  - the slider writes `(mouseX - (x + 4)) / (width - 8)` with `width = 150`, quantizing to the **1/142 grid** (finer and offset at GUI scale > 1). Real `options.txt` values in the wild are exactly `49/142`, `57/142`, `36/142`. Step = `200/142 ≈ 1.408 %`, so 58 of the 199 integer percents (3, 6, 10, 13, 17, 20, …) are unreachable
  - `0.0`/`1.0` are special-cased to `*yawn*`/`HYPERSPEED!!!`, so `0%`/`200%` never show

  ⇒ the drag-drop rewrite is the ONLY exact path, and touching the slider afterwards destroys the written precision. The percent is a sanity read; `mc_hipfire_file` is the deliverable. The FEEL is non-linear — `calc_sens_mc` inverts the cubic `(.2 + .6 * s)³ × 1.2°`
- MC rewrite FORCES the view: `fov:` gets the literal `1.0`, `fovEffectScale:` gets `0.0` (no sprint/speed FOV pumping) and the two shake keys get zeroed: `bobView:` → `false` (walk/step camera bob, Video Settings) and `damageTiltStrength:` → `0.0` (the hit tilt, Accessibility Settings, 1.19.1+). **The two are INDEPENDENT** — `bobHurt()` is called outside the `bobView` gate, so turning View Bobbing off leaves the damage tilt running; a pre-1.19.1 file simply has no `damageTiltStrength:` line and that one replace no-ops. MC's slider is vertical FOV = 70 + `fov` × 40 (±1 ⇒ 30–110°), so `1.0` IS the 110 `constants.fov.mc.hipfire` assumes — MC FOV is NOT user-selectable, and changing `hipfire` means changing that literal. All five MC keys are `\n`-anchored lookbehinds (`(?<=\nfov:)` can't hit `fovEffectScale:`); the four numeric ones accept a leading `-`, `bobView:` takes a `\w+` boolean
- Files rewritten: PUBG `GameUserSettings.ini` (sens map, `FpsCameraFov`, and `MouseVerticalSensitivityMultiplierAdjusted` reset to `1.000000`), MC `options.txt`, R6 `GameSettings.ini` (the searched `MouseYawSensitivity` int, written to `MousePitchSensitivity` as well, + unit + ADS ints). Neither rewrite reads the CPI pair — no vertical value depends on it (`calc/CLAUDE.md:No vertical fields`). The `[dragover]` box takes BOTH paths: `drop` reads the dropped file, and **`click` copies the game's config FOLDER to the clipboard** (`navigator.clipboard.writeText` + a `Copied!` toast) before opening the file picker — paste it into Explorer's address bar. The clipboard string is the directory; the box's `:hover:after` tooltip is the same path WITH the filename. Both are typed literals per game, so they move together. Neither path writes in place — the rewritten copy comes back as an `a[download]`, and the user replaces the original. The three `download_updated_*_file()` functions end in the same blob→`a[download]`→revoke tail; it is duplicated on purpose so each keeps its own filename constant beside its own regex set

## Game sens sync
`update_game_sens()` is ONE module-private, zero-param function: reads `{cpi_scale, height, pubg_fov, width}` off `state.game` (NOT `ads_scope` — no cell follows the ADS selector), derives every value into locals, then `set_text_if_changed`s all 79 cells. Adding or changing a displayed value touches exactly TWO places — this function and `dom.js`. Values are computed on the GAME-resolution basis (`state.game.width / cpi_scale`), never the canvas. Its local const band is dependency- and game-ordered, not alphabetical — one semantic block per game.

It ran in `worker/calc_worker.js` until 2026-08, shipping a positional number tuple (60 values then) whose order had to match across four files (worker push order, `manager.js` cast, a 60-param controller signature, `dom.js` refs); a partial edit silently desynced displayed values. The whole card measures ~0.18 ms, so the worker bought nothing — **don't reintroduce the hop** (`worker/CLAUDE.md`).

## Non-obvious
- `contextmenu` is preventDefault'd globally so RMB is usable as game input
- **There is no in-game controls panel.** `#controls` (bottom-left `[hud]`, guide line + 5-row key grid, auto-faded by a `controls-fade` keyframe) was deleted in 2026-08 once `tutorial.js` shipped — with `hud.set_controls()`, both `controls_*` refs, the keyframe and all eight `constants.mode.*.guide` strings. Nothing in a run explains itself now; the tour does. `[hud]` still gates the two remaining blocks (peak/accuracy/crit, timer/fov/sens)
- `keydown`/`keyup` short-circuit when `is_keyboard_control(ev)` finds an input/button/select/textarea/contenteditable/`x-select` in `ev.composedPath()` — settings controls keep working while the screensaver timer still resets. `keydown` ORDER matters: `defaultPrevented`/`repeat` bail first, then `Escape` + `is_modal_active()` (`#bg[activate]` or `#setting-view[active]`) → `on_click_modal_backdrop()`, and only then the control check — so Escape closes a modal even from a focused input
- Q/W/E/R/A keydown ALSO calls `mode.shoot()` immediately besides setting `state.input.key_*`. Tracking modes additionally read those flags in `on_frame()` for continuous movement + shots
- RMB is dual: when `is_ads_available(mode)` — the mode defines `update_dimension` AND `logic.js:ads_stage_count() > 1`, which rules out `lol` — it fires `update_dimension` on down AND up AND `mousecancel` — must be idempotent. Otherwise RMB acts as `shoot()`. The `ads_stage` write sits INSIDE that same branch, so a mode without `update_dimension` (`aim_booster`/`writing`) or any mode under `lol` never moves the stage and never re-runs `update_camera_view()`; the same predicate decides whether `on_mousemove` pitch-clamps the 2D `y`. (`lol`'s RMB was a 2D→fpp flip until 2026-09-05 — League has no ADS, so it now shoots and the run stays 2D)
- **`state.input.ads_stage` (`AdsStage` = `0 | 1 | 2`) is the LOGICAL ADS state; `mb_right` stays the RAW button.** `logic.update_camera_view()` reads ONLY `ads_stage` — in toggle mode the player is scoped while the physical button is up, so reading `mb_right` there would drop them out of ADS. `mb_right` is still correct for what it is: `writing.js` fires on it, `on_mouseup` gates on it. `window.js` owns the helpers:
  - `is_ads_cycled()` — `true` for `sa` ALWAYS (TRG has no hold option) or when `state.game.ads_toggle` is set. Cycled ⇒ RMB down advances the stage, up does nothing; hold ⇒ down sets `1`, up sets `0`. **Cycle-vs-hold and stage COUNT are independent axes — do not derive one from the other.** Being two-stage is NOT why `sa` is forced to cycle: `val`'s Operator is two-stage too and Valorant does offer hold, so `val` honours `ads_toggle` like everything else. `sa` is forced because the GAME has no hold option
  - `cycle_ads_stage()` — `(stage + 1) % stage_count`, and `stage_count` comes from `logic.js:ads_stage_count()`, NOT from a chain here: `1` for `lol` (no ADS — RMB shoots), `3` for `sa` always, `3` when the selected weapon has a `constants.fov.<game>.ads_stage2` entry (`cs2` AWP/Automatic, `val` Operator), `2` otherwise. **A third stage is reachable ONLY in cycle mode** — the honest consequence of the two axes being independent: hold gives you one stage, so an Operator or an AWP on hold stops at its first zoom. The `% stage_count` keeps a stale `2` from a previous 3-stage run out of a 2-stage game
  - reset points: `mousecancel` (blur can't strand you scoped) and `logic.start_game()` before `init()` — without the latter, a leftover ADS stage leaks into the next mode's first `update_camera_view()`
- `state.game.ads_toggle` (default `false` = hold) is a GLOBAL input preference bound in `setting.js`, not a per-game card field — the player matches whatever their game is configured to. `sa` ignores it. It is also the gate on every SECOND zoom stage a game offers, because a hold cannot express one
- `mousecancel` is NOT a native event — `on_blur()` (window `blur`: alt-tab, OS dialog, devtools) dispatches it so `mb_left`/`mb_right` can't stay stuck true. `on_blur()` also zeroes every `state.input.key_*` directly (same risk, no event contract needed since nothing outside `window.js` listens)
- **Mouse movement arrives through `pointerrawupdate`, not `mousemove`, wherever the browser has it** (`HAS_POINTER_RAW_UPDATE = "onpointerrawupdate" in document`; Chromium 85+, Firefox 131+, not Safari; `private.d.ts` augments `DocumentEventMap` so the listener stays typed). `mousemove` is coalesced to one event per rAF, so a click landing mid-frame was judged against a position up to one frame stale (4 ms at 240 Hz); raw updates fire as the OS delivers them, in order with `mousedown`, and their `movementX`/`movementY` still sum every sample since the last dispatched event. The handler is the same `on_mousemove` and stays a bare delta accumulate, because it now runs at the mouse's polling rate (1 000 to 8 000 Hz). Without support the init block falls back to `mousemove` AND shows `#browser-notice` under the logo — a bilingual prose line (`lang_text`, re-rendered on `lang_select` `change`, which `setting.js` handles first since it is evaluated first) telling the player to install Chrome; the app stays usable. Only ONE of the two events is ever bound, or every delta would count twice
- `on_mousemove` reads the cached `state.camera.sens`, kept current by `logic.update_camera_projection()` — which `on_resize()` calls on every resize — and ends with `game_mode[mode].on_move?.()`, the per-delta hook only `writing` implements. Changing `calc_rad_per_px` moves both the sens displays and aim feel
- 2D mouse move clamps `y` to `±(PI/2/sens - EPS | 0)` (int px); 3D clamps `pitch` to `±(PI/2 - EPS)` rad
- Pointer lock loss in-game ⇒ `stop_game()`; lock/fullscreen failure at start ABORTS `start_game()` (root `CLAUDE.md`)
- Screensaver: 5 s after input idle, mouse OR keyboard — every input handler calls `reset_screen_saver_timer()` (`constants.screen_saver.delay_ms`). Armed only outside a game (`!state.game.mode`; an open modal does NOT block it). `state.game.rest_timeout` is TRI-state, not just a timer id: `>0` pending `setTimeout`, `-1` currently resting (so the next input removes `body[rest]` instead of clearing a timer), `0` neither. `body[rest]` drops the `brightness(.85)` BG filter and hides UI via `[rest]>:not(#bg-preview,#bg,main)/none`, while `main` fades to `op=.3` (`op=0` on coarse pointers) — leaving the unfiltered 3-strip video
- Default BG pipeline: `render/renderer_bg.js` transfers `#bg-video-canvas` through `manager.js` to `bg_worker.js`; the worker builds a looping `MediaSource` from `bg.mp4` and returns a `MediaSourceHandle`; the main thread plays it in a hidden video and posts one `VideoFrame` per `requestVideoFrameCallback()` tick. Avoid `captureStream()` — it can cap/drop frames

## When you change…
- Add a DOM element: `dom.js` ref → init from `state` in `main.js` (if state-backed) → bind in the owning controller
- Add a mode button/score: `dom.js` · `menu.js` · `setting.js` clear-score wiring · `tutorial.js` step · the mode's own module-load `set_mode_score()` + localStorage key (`main.js` does NOT touch best scores)
- Add a settings section: `dom.js` ref · `tutorial.js` step + the count in the `setting_btn` step (the tour walks every `fieldset[id^='setting-']` but does not generate the steps)
- Add a sens display value: `update_game_sens()` (compute + write) · `dom.js` ref · markup
- Add an ADS scope option: `constants.fov.<game>.ads` key · the matching `ads_ref` key if that game shares ONE typed field (`cs2`/`rb`/`val`) and an `ads_stage2` key if it has a second zoom · an `<li data-value>` in that card's `#<game>-ads-scope` · nothing else — `state.js:read_ads_scope`, `logic.update_camera_view()` and `calc_sens_snap` all read the maps
- Input behavior: `window.js`; mode-specific shot logic stays in `game_mode/*.js`
- BG/crosshair settings: `setting.js`; defaults from `state.js`/`constants.js`; default-video transport in `render/renderer_bg.js` + `worker/bg_worker.js`; upload library in `setting.js` + `bg_store.js`
