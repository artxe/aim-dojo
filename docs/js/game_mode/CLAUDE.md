# game_mode/

Each mode default-exports `/** @type {GameMode} */`. `index.js` maps `GameModeName` → that default through 4 getters. Imports are STATIC, so every mode's module-load side effect (its `set_mode_score()` write) runs at boot regardless — the getters shape the record, they do not defer loading.

## Mode contract
```
init()              reset state; set_hud_labels() for this mode's units; call update_camera_view() FIRST, then build initial target(s) per dimension
on_frame()          read input/timer; advance targets/lerps; tracking modes call shoot() here
on_move?()          after every mouse delta lands in state.camera (pointerrawupdate, so polling-rate) - writing extends its stroke here; keep it a few comparisons
render()            2D context_2d, or prepare_3d_view() → draw_*_3d on #canvas-3d → draw_crosshair() on the 2D canvas
shoot()             evaluate hit/crit; play SFX; push to impacts/impacts_3d; push to state.stats.shoots
update_hud()        write peak/best/accuracy to DOM; set state.hud.next_update_ms = now + constants.hud.update_interval_ms
dispose()           clear state; state.game.mode = null; reset_hud_labels(); reset state.impact.rad_size; clear per-dim impacts
check_stats?()      drop expired shoots + decrement aggregates (only when HUD is due, not every frame)
update_dimension?() RMB down/up + mousecancel — must be idempotent
```

## 2D vs 3D
| modes | dimension |
|---|---|
| `aim_booster`, `writing` | always 2D, no `update_dimension` |
| `h_tracking`, `precision` | 2D/3D capable |

- The fixed-dimension modes STILL call `update_camera_view()` first in `init()`, then override — it is what populates `state.camera.sens`/`fov`/`sens_error`, which the HUD's view and `error` lines read even in 2D. **Their 2D cursor is NOT pitch-limited**: `on_mousemove` clamps `y` to the ±90° pitch range only when `is_ads_available()` — a mode that defines `update_dimension` in a game with an ADS stage, so not under `lol` either (it must stay convertible to 3D); `aim_booster` boxes `x`/`y` to the monitor itself every frame and `writing` scrolls freely (2026-09-05). That call also sets `state.impact.rad_size`, so their `dispose()` resets it like the 3D-capable modes. Nothing after the override needs a second `update_camera_projection()` — it no longer reads `dimension` (it did for the `sens_error_v` line, gone 2026-09-05)
- `aim_booster`/`writing` never call `update_camera_view` again mid-run and force only `dimension = "2d"` — they leave a tpp game's `dist` in place, harmless because nothing in a 2D frame reads `px_to_rad`
- A mid-run resize is safe for every shape because `on_resize()` uses `update_camera_projection()`, which re-derives `vfov`/`fov`/`sens`/`rad_size` for the new aspect off the stored `fov_axis`/`view_fov` plus the CURRENT (overridden) `dist`, and never rewrites `dimension`/`dist`. **That split exists FOR these overrides — do not "simplify" `on_resize()` back to `update_camera_view()`**
- Effective dimension = whatever `logic.update_camera_view()` returns for `state.game.sens` + `state.input.ads_stage` (NOT `mb_right` — `controller/CLAUDE.md`). `lol` is 2D only (its RMB shoots, `controller/CLAUDE.md`), `bdo`/`mc` toggle tpp↔fpp, `fn` stays tpp for BOTH `ADS` views and only `Scoped` goes fpp (the orbit pulls in, `tpp.fn` 3 → `tpp.fn_ads` 1), `pubg` uses tpp-80 or fpp-103 hipfire with fpp ADS, `al`/`cs2`/`ow`/`r6`/`rb`/`val` stay fpp and only change `fov`, `sa` cycles hipfire→TRG x5→TRG x15 (3 stages, the only game reaching `ads_stage == 2`)
- `update_dimension()` body order: `update_camera_view()` → convert camera if `x`/`y` or `pitch`/`yaw` is non-zero → convert active target(s) → convert ANY in-flight lerp endpoints (`size_lerp.from/to` in `h_tracking` are stored in current-dim units)

## Stats flow (shared `state.stats`)
- `shoots` entries are `{ s, e, h, c }` — start/end stamps of the scored interval, hit, crit. Instant-shot modes (`aim_booster`/`h_tracking`/`precision`) use `s = prev_ms`, `e = now_ms`
- `shoot()` pushes one entry and bumps aggregates: all modes increment `count_*`; `h_tracking` also adds `e - s` to `sum_shoot_ms`/`sum_hit_ms`/`sum_crit_ms`. `aim_booster`/`precision` are count-only
- `h_tracking` calls `shoot()` every frame an input key is held → many tiny windowed entries
- `check_stats()` drops entries with `e < now - 30 s` (decrementing aggregates) and clips entries straddling the window edge: `first.s = window_ms` plus a partial `sum_*_ms -= window_ms - s`
- **`aim_booster` keeps TWO queues, and they answer different questions.** `state.stats.shoots` (shared, pooled) is the 30 s stats window like every other mode; `history` is module-local and holds nothing but a `now_ms` per shot, for the 10 s REWIND. They were one queue until the split, which is why its `Accuracy` used to be a whole-run number while everyone else's was windowed — the queue could not expire without destroying the rewind. `trim_history(until_ms)` is the ONE truncation rule, called from `dispose()` and from the in-run overload rewind; neither touches `state.stats` any more, because the window expires itself
- **`writing` samples the pen per mouse delta, not per frame.** `shoot()` (LMB/RMB/key press from `window.js`) STARTS a stroke at the crosshair; `on_move()` (every `pointerrawupdate` while a fire input is held) calls `shoot()` again, which appends a segment only once the crosshair has moved at least `line_width` px from the last pushed point — shorter than the pen is invisible, and it caps the ring at stroke-length-in-px segments instead of one per raw event (8 000 Hz mice) or one per frame; `on_frame()` only expires old segments and ends the stroke on release. Fast strokes are now traced at pen-width resolution instead of one chord per frame
- `writing` does not use `shoots` at all: `init()`'s `build_text()` posts `text_data` + dims ONCE per run via `set_writing_text` with the buffer TRANSFERRED (main thread must not reuse it). `check_stats()` then sends a DELTA — a transferred `Float64Array` of only the strokes added since the last tick, plus `drop_count` for the ones that aged out — to `writing_worker.check_writing_stats`, which keeps its own ring, rasterizes to an OffscreenCanvas, compares alpha against the cached `text_data`, and returns `[count_hit, count_shoot]` for `writing`'s handler to write into `state.stats`. `pending_drop`/`pending_push` are the two counters that make the delta work; `dispose()` must zero both

## Scoring — every mode reports a MEASUREMENT, not points
| mode | number | unit |
|---|---|---|
| aim_booster | Fitts throughput (below) | bit/s |

**`aim_booster` targets LIVE and DIE on a clock.** Each spawns at radius 0, grows to half of `target_diameter` over `target_grow_ms` and shrinks back to 0 over another — `r = target_diameter / 2 * (1 - abs(age / target_grow_ms - 1))`, rewritten every frame in `on_frame()` so the hit test and the draw always agree. At `age >= target_grow_ms * 2` it expires, costs a LIFE and leaves the MISS effect — `play_miss()` plus a `c: void 0` impact from `impacts_pool` at the target's own position, the same pair a click into empty space produces, so a life lost looks and sounds like the miss it is.
- **`target_diameter` is a DIAMETER and the spawn box is inset by it**: `(random() - .5) * (grid_width - target_diameter)`, so a disc at full size still sits inside `grid_width` × `grid_height` (600 × 420, centred) instead of half-hanging off it. The box is the SPAWN range only — `grid_pattern` still covers the whole canvas
- **The core is concentric and worth nothing.** `cx`/`cy` are the target's own position and the mode never tests crit; it is `r * core_ratio` (.2), a small dot marking the centre of a disc whose edge keeps moving — NOT `calc_core_radius(r)`, which is half the radius and swallows the target
- Lose all `lives` (3) and the spawn rate rewinds `rewind_s` (20 s), every live target is recycled and the lives come back — the same machinery the old "backlog too big" rule drove, on a criterion the player can actually see. `draw_lives()` writes them one line under the rate text, inheriting the `fillText` colour set right above the call. **A lost life becomes a HOLLOW heart rather than disappearing**, so the row keeps its width and you read the remaining count at a glance instead of counting what is left: `LIFE_TEXT[n]` is `n` × `♥` then `lives - n` × `♡`. It is a module-level table sized from the `lives` constant, not a `repeat()` per frame, and `lives` can never index outside it — the `lives <= 0` rewind runs in the SAME `on_frame()` as the decrements, so `render()` only ever sees 1..`lives`. `♥` is WGL4 and lives in every Windows core font; `♡` is NOT, so it arrives through the browser's per-glyph fallback (Segoe UI Symbol) and can differ slightly in weight
| h_tracking | `track_bits / elapsed_s` | bit/s |
| precision | Fitts throughput (below) | bit/s |
| writing | `count_hit ² / count_shoot / (window_ms / 1000)` | on-text px/s |

**`/s` means `/s`, so the denominator is the span the window ACTUALLY covers** — `min(now_ms - state.timer.start_ms, window_ms) / 1000`, not a hardcoded 30. For the first 30 s of a run the window is only as old as the run, and dividing by 30 there understates every rate. `precision` needs no such denominator: `ID_e / MT` is a rate by construction.

The old arbitrary point formulas (`100 * (crit + hit) * hit / shoot`, `count_hit * 100`, `7 * hit * accuracy⁴`) are gone. They had no unit, were not comparable across sessions once any tuning constant moved, and could not answer the question the app exists for — which sensitivity aims better. A number with a unit can. **Three of the four share bit/s and ARE comparable with each other**; `writing` cannot join them — tracing a path follows the STEERING law (Accot & Zhai), whose index is `A / W` rather than `log2(A / W + 1)`, so its rate is `1/s`, not bit/s. **There is deliberately no combined rating**, even across the three that share the unit: averaging them would hide the very thing the app is used for, that the sensitivity peaking in `aim_booster` (gross, ballistic) is NOT the one peaking in `precision` (fine, corrective). A single number would average that difference away.

**A run banks ONE sample: its own mean, never the live HUD peak.** `update_hud()` adds the live score into `run_sum`/`run_count` on every tick where **the score is non-zero**, and that IS the whole gate: a rate of `0` means you were not shooting, a throughput of `0` means the window holds fewer than `constants.fitts.trial_min` trials, and neither is a measurement worth averaging. `dispose()` pushes that run's `run_sum / run_count` into the mode's `create_record` (`struct/record.js`), which keeps the ALL-TIME MAX of every sample ever pushed as `value`, persisted as a single number (`String(record.value)`) under `<name>#runs`. **What a mode DISPLAYS is that running max**, so it only ever moves up (until `clear_score()`) — a genuine personal best, matching what a player expects after seeing a higher number on the live HUD (a prior trimmed-mean-of-last-10 design moved the display both ways and confused players when a clearly better run didn't raise it). The per-run averaging step still matters even though the cross-run stat is now a max: banking a run's raw peak tick instead of its mean would let one lucky spike — or a longer run, which just gets more chances at one — inflate the record; `run_sum / run_count` keeps that noise out of the one number that gets compared against history. `struct/record.js:parse_value()` still reads a legacy comma-joined ring from an existing user's `localStorage` and takes its max, so nobody's saved score resets to `0` on upgrade.

**The gate used to be `now_ms - start_ms >= window_ms`, and that was a bug**: it threw away EVERY run under 30 s whole — no run average, no banked sample, so a short session left the record at `0` and looked broken. It is also unnecessary, because the rate modes already divide by `min(elapsed, window_ms)` and throughput never depended on a full window at all. There is exactly ONE `localStorage` write per run instead of the old `best_score_dirty` flag guarding 20 writes/s in the frame loop, and `dispose()` is a reliable bank point because losing pointer lock — Escape, tab hidden, fullscreen exit — routes through `on_pointerlockchange` → `stop_game()` → `dispose()`. Score display + Clear-button enablement ALWAYS go through `dom.js:set_mode_score(<name>_score_el, clear_<name>_btn, value)`; the three call sites are module load, `clear_score()` (0) and `dispose()`'s bank.

### h_tracking throughput
- **`move.speed` is base-radii per ms and no longer scales with the LIVE target radius** — `base_radius * move.speed`, or `px_to_rad(base_radius) * move.speed` in 3D. It used to be `target.r * move.speed`, which made a 15× target sweep ten times faster than a 1.5× one: size and speed were ONE axis, and every normalised measure cancelled the size out algebraically. They are independent now, which is what lets a single number see both
- Every `move_change_interval_ms` the target reverses or re-rolls its speed, so one interval IS a corrective movement of amplitude `A = |speed| * T` to a tolerance `W = 2r` ⇒ `ID = log2(A / W + 1)` bits, `ID / T` bits per second DEMANDED. `shoot()` accumulates `ID / T * ms` into the entry's `d` only while the crosshair is on the target, so the score is the share of that demand you actually met — the same bit/s as `precision`
- **The ratio is dimensionless, so 2D and 3D give the same number** with no px↔rad conversion: `A / W` collapses to `abs(move.speed) * T / (2 * size_mul)`, `size_mul` being the live size step
- `check_stats()` subtracts `d` as entries age out, with a proportional `cut` on the partial-window clip (and `first.d` reduced to match, or the later full expiry would subtract it twice), so `track_bits` always matches the live 30 s window
- **`on_frame()` runs ONE size-lerp/speed-lerp block for both dimensions** through `t = dimension == "2d" ? target : target_3d` — `r`/`cr` are the fields `Target` and `Target3D` share — with `base` = `base_radius` (px) or `px_to_rad(base_radius)` (rad) computed once per frame instead of three times. Only the movement axis (`target.x` vs `target_3d.y`) and the core placement stay per-dimension (the 2D/3D copies were byte-identical apart from those until 2026-09)
- Retuned with the decoupling: `base_speed` .01 → **.06** preserves the mean ABSOLUTE speed of the coupled build, and `size_steps` narrowed to `[1.5, 2, 3, 5]` — a 10× size spread against ONE speed knob has no setting that suits both ends, the 15× target was free while the 1.5× one stayed brutal

### aim_booster throughput
`aim_booster` is serial pointing — the protocol Fitts' law was written for — so it reports the same `TP = ID_e / MT` as `precision`, sharing `constants.fitts` (`trial_min`, `we_factor`).
- **One trial per CLICK, not per kill.** `D` is measured from the PREVIOUS click position to the target's centre, `MT` from the previous click's timestamp; `struct/fitts.js` carries that previous click — `fitts.trial(target_x, target_y, x, y, now_ms)` closes a trial toward the attributed target and becomes the previous click, `fitts.click(x, y, now_ms)` just becomes it when no target is live — and the first click of a run opens no trial because there is no previous point
- **A miss is attributed to the NEAREST target**, so it lands in the scatter instead of vanishing. Dropping misses would inflate `TP` by removing exactly the worst endpoints — the same loop that looks for a hit tracks the nearest index, so it costs nothing. Standard practice is to include every trial, and this is the closest honest reading when several targets are live and the intended one is ambiguous
- Picking easy targets does not help: a near target lowers `D` and therefore `ID`, and dawdling raises `MT`. The spawn-rate ramp no longer enters the score at all — it is now purely the difficulty driver, still shown live in the `Spawn` slot

### precision throughput (ISO 9241-411)
Same protocol as `aim_booster`, sharing `constants.fitts`: `TP = ID_e / MT` in bit/s over the same 30 s window.
- **One trial per CLICK.** `D` runs from the PREVIOUS click position to the target's core, `MT` from the previous click's timestamp, and `struct/fitts.js` carries that across shots (`fitts.trial(t.cx, t.cy, x, y, now_ms)` in 2D, `fitts.trial(t.cy, t.cp, yaw, pitch, now_ms)` in 3D; `fitts.click()` when the array is momentarily empty). The first click of a run opens no trial, having no previous point
- **It used to be one trial per target's FIRST shot**, which tied the trial rate to the KILL rate: a target that took several shots produced ONE trial, and the window could sit under the `trial_min` floor and pin the score at `0`. Per-click also matches ISO serial tapping, which counts every click, and matches `aim_booster` — one protocol, one reading
- The endpoint error is the SIGNED projection onto the movement axis (previous click → target core), positive = overshoot. The scatter of those signed errors is the whole measurement: `W_e = we_factor * SD` (`4.133`, the 96 % band of a normal) and `ID_e = log2(D / W_e + 1)`. That is what makes throughput ungameable — rushing widens the scatter as fast as it shortens `MT`, and creeping lengthens `MT` as fast as it tightens the scatter
- **`W_e` comes from the shots, NOT from the target radius**, which is why the staircase can move the target size mid-window without touching the number, and why the difficulty multiplier the point formulas needed no longer exists
- Sums (count/dist/err/err²/ms) live INSIDE `struct/fitts.js:create_fitts()`, maintained incrementally: `trial()` adds, `expire(until_ms)` (called from `check_stats()`) subtracts as trials age out, so `throughput()` is O(1). Trials are pooled into a queue the struct owns — the shared `shoots` queue keeps its own `{c,d,e,h,s}` shape for accuracy/crit. `aim_booster` and `precision` are the two users and share every line of it (they carried two byte-identical copies until 2026-09). **`trial()` skips a zero-distance OR zero-time trial**: two `shoot()`s in one frame (LMB + Q) share `now_ms`, and a 0 ms trial is `TP = ∞`, which would have poisoned `run_sum` and the persisted record
- **Below `trial_min` (5) trials in the window there is no measurement, so the HUD shows `-` and the run banks NOTHING** (`throughput()` returns `0` there and both modes print `-` for a `0`). `W_e` is an SD estimate and a variance from two or three samples is noise, but a silent `0` reads as "your throughput is zero" rather than "not enough data yet" — and a `0` folded into `run_sum` would drag the run average down every time you stop shooting long enough for the window to drain. The floor was 10 while a trial cost a whole cleared TARGET, which is what made the readout look stuck at zero
- `update_dimension()` calls `fitts.reset()` (forgets the previous click) — the click position is px in 2D and rad in 3D, so a trial cannot straddle the switch
- `MT` includes reaction time (the target APPEARS, it is not pre-visible as in ISO's serial tapping), so absolute numbers read a little below a lab pointing study. The bias is constant, so comparisons across sensitivities and sessions still hold

### precision spawn
One small static target at a time, 2D and 3D alike, respawned by `on_frame()` the moment `shoot()` empties the array — a run is a continuous arrive-stop-fire loop with no reaction or search phase.
- **Size and distance are INDEPENDENT knobs, and that is the whole design.** `r = base_radius * target_radius_mul`, while the throw is `(near_dist_mul + random() * (far_dist_mul - near_dist_mul)) * base_radius` — the distance never scales with `r`, so shrinking the target really does raise the difficulty instead of pulling the spawn in with it
- **The core is `calc_core_radius(r)`, the ONE-arg form — never `calc_core_radius(r, base_radius)`.** The two-arg form floors the core at `base_radius / 2`, which at a `target_radius_mul` below 1.5 is bigger than `r` itself: every hit would score as a crit. One arg gives `r / 2`, a fixed ratio that survives any size
- `random_theta(origin, dist, range)` picks the direction: `atan2(sin(theta) * .2, cos(theta))` flattens it toward the horizontal, and when the throw could leave ±`pitch_limit` it samples uniformly OUTSIDE the forbidden arc rather than clamping — a clamp would pile spawns onto the limit line. `origin` is where the shot starts (`y` in 2D, `pitch` in 3D), so the range test always runs against the current aim

## Per-mode pooling (see root `CLAUDE.md:GC avoidance`)
- `shoot()` does `shoots_pool.obtain()` → assign EVERY field (`c`/`e`/`h`/`s`) → `push`. Never push a literal; always set `c` even on a miss (`c = false`), or a recycled object's stale crit flag leaks
- `check_stats()` recycles on the full-expire branch only, AFTER `shoots.drop()`. The partial-window clip (`first.s = window_ms; break`) keeps the entry live — do NOT recycle there
- Targets: `precision` keeps `target_pool_2d`/`target_pool_3d`, `aim_booster` keeps `target_pool`. Spawn `obtain()`s + fills; removal `recycle()`s the removed object (manual shift instead of `splice`/`length--`); a bulk `length = 0` recycles every entry first. `update_dimension()` `obtain()`s the destination, runs `convert_target_*(t, out)`, then recycles the source
- `h_tracking` keeps `target`/`target_3d` as single `const`s converted in place
- `dispose()` releases: `reset_run_state()` clears the shared `shoots_pool`/`impacts_pool`/`impacts_3d_pool`; modes with target pools clear theirs too. `aim_booster` calls `reset_run_state()` in both `init()` and `dispose()` like everyone else now that its stats live in the shared window; its `history` holds numbers, so there is nothing to pool or recycle there
- `writing` has NO objects and NO pool: strokes live in a module-level `Float64Array` ring (`lines`/`lines_head`/`lines_tail`, `LINE_STRIDE` 5 = `ex,ey,sx,sy,t`) written by `push_line()`, which doubles or `copyWithin`-compacts when the tail runs out. That removed the last per-frame allocation in the hot path — `shoot()` is called on every qualifying mouse delta while a key is held, so the old `lines.push({ … })` literal allocated at input rate. `render()` and the worker payload both index the array directly; there is nothing to recycle

## Mode state landmarks
**`state.js` is for cross-cutting runtime state only. Each mode owns its own state — including its persisted run record — at module level.**

Every mode file has: `const STORAGE_KEY = "<name>#runs"` · `const record = create_record(localStorage.getItem(STORAGE_KEY) || "")` · `let run_count`/`let run_sum` (the run's own mean, reset in `dispose()` AFTER the bank) · a module-load `set_mode_score(...)` · `function clear_score()` (`record.clear()` + `removeItem` + `set_mode_score(..., 0)` + a mode-specific `send_toast`), included in the default export and called directly by `controller/setting.js`.

- Targets — `aim_booster`: `const targets` + `target_pool`. `precision`: `const targets, targets_3d` + both pools, one live entry at index 0. `h_tracking`: `const target, target_3d`, converted in place via the `out` arg. `Target = {x,y,r,cx,cy,cr}`, `Target3D = {y,p,r,cy,cp,cr}` (y = yaw, p = pitch)
- Lerps (`h_tracking`): `const size_lerp`, `const speed_lerp` — `{active, from, to, start_ms}`, endpoints in current-dim units
- Move (`h_tracking`): `const move` — the horizontal axis (`target.x` / `target_3d.y` yaw) with a core rotating toward movement
- Timers (`h_tracking`): `let next_change_*_ms`, `next_impact_ms`
- `aim_booster` extras: `let count, end_ms, start_ms` + a module-local `const history = create_queue()` of plain `now_ms` numbers. `end_ms`/`start_ms` and the truncated `history` PERSIST across `dispose()` (dispose sets `end_ms`, leaves `start_ms`) to drive the 10 s rewind on the next `init()`; `count` is reset in `dispose()` and recomputed in `init()`. Session-scoped — a page reload resets it
- `writing`: `let lines` (the `Float64Array` ring) + `lines_head`/`lines_tail` + `pending_drop`/`pending_push` (worker delta counters), `let has_pointer`/`pointer_x`/`pointer_y` (last stroke endpoint; `has_pointer = false` breaks the path), `let text_image` (rebuilt each run by `build_text()`, which shuffles `constants.mode.writing.sentences` in place and redraws into the reused module-scope `off` canvas; `dispose()` closes `text_image`)

`create_queue()` is exported from `struct/queue.js` for module-local queues — `aim_booster.history` and `struct/fitts.js` are the users.

## localStorage key conventions
- `<a>.<b>.<c>` (dots) = the `state.<a>.<b>.<c>` path; `state.js` owns read/write. E.g. `bg.type`, `crosshair.color`, `game.lol_sens`
- `<module>#<field>` (hash) = module-private persisted field; only that module touches it. E.g. `precision#runs` (ONE number, the all-time max run mean; `struct/record.js` still parses a legacy comma-joined ring). `state.js` does not know about these; a mode with adaptive difficulty adds `<module>#level` beside it

## Footguns
- `update_dimension()`'s old-dimension branch is captured BEFORE `update_camera_view()`, so it must bail if `state.camera.dimension` is STILL `"2d"` after that call — every 2D/3D-capable mode starts with `if (state.camera.dimension == "2d") { return }`. Idempotency is required (RMB down/up/`mousecancel` can all fire with no real transition); without the guard a redundant call still runs the one-way 2D→3D conversion, stranding live targets in the inactive array and double-applying `px_to_rad`/`rad_to_px` to any active lerp
- Forgetting `state.impact.rad_size = 0` in a 3D-capable `dispose()` leaks the impact radius into the next mode
- Forgetting to clear `impacts` vs `impacts_3d` per the disposed dimension leaves stale visuals
- `update_dimension()` while a lerp is active and NOT converting its endpoints visibly snaps target size/speed
- 3D `render()` calling `draw_*_3d` before `prepare_3d_view()` draws with the previous frame's matrices — and now also skips the per-frame uniform re-upload entirely, since `prepare_3d_view()` is what bumps the renderer's `frame_id` (`render/CLAUDE.md`)
- 2D `render()` must open its OWN `save()` + `translate(-x, -y)` around the world block and close it before `draw_crosshair()`: the `draw_grid`/`draw_target`/`draw_impacts`/`draw_aim_guides_2d` helpers no longer transform or `save`/`restore` themselves, so without that pair the world draws un-panned AND their `globalAlpha`/`strokeStyle` leaks into the crosshair
- `check_stats()` mutates `first.s` in place during the partial clip — treat `shoots.at()` as a live reference, not a copy
- Module-local state is NOT auto-reset between runs. `dispose()` MUST reset every per-run `let`/queue/array. `aim_booster.end_ms`/`start_ms` + its truncated `shoots` are the deliberate exceptions
- Pool correctness: every `obtain()` must set ALL fields; every removal must `recycle()` exactly once (double-recycle puts one object at two live slots)
- Adding a mode: wire its clear button directly to `game_mode.<name>.clear_score` in `controller/setting.js`
