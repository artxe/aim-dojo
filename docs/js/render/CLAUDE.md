# render/

Two SEPARATE stacked canvases, never composited: `#canvas-3d` (transparent WebGL2) beneath `#canvas` (2D, topmost). `logic.on_frame()` shows/hides `#canvas-3d` when `state.camera.dimension` crosses `2d`. In a 3D frame the mode clears the 2D canvas to transparent and draws only `draw_crosshair()` on it, so the crosshair overlays the 3D scene showing through.

## Files
- `camera.js` — 2D px ↔ 3D yaw/pitch rad conversions + hit tests (`dimension` is owned by `logic.update_camera_view()`, not here) + `calc_camera_sens(fov_deg)`, the ONLY producer of `state.camera.sens`, called ONLY by `logic.update_camera_projection()`
- `mat4.js` — 4×4 matrix math; imports `../math.js` only. Exports take the destination array first
- `renderer_2d.js` — grid, impacts, targets, crosshair, dynamic crosshair image
- `renderer_3d.js` — WebGL2 grid/targets/impacts/strokes on `#canvas-3d`
- `renderer_bg.js` — BG video canvas: transfers `#bg-video-canvas` to `bg_worker.js`, handles worker `MediaSourceHandle`/frame acks (`on_bg_worker_message`), `resize_bg()`, `set_bg_video_visible()`, audio enable/volume. Also owns the upload path via `set_bg_upload_video(blob|null)` — a plain fullscreen `#bg-upload-video` `<video loop>` (object URL revoked on swap), NOT routed through the worker. `update_bg_video()` branches on `state.bg.type`: `default` plays the hidden MSE frame-source video (→ worker tiler), `video` plays the upload element, `youtube`/`none` pause both
- **Pausing the frame-source video breaks the frame pipeline, so EVERY resume has to re-arm it — `update_bg_video()` owns that, not the caller.** A `requestVideoFrameCallback` stays registered on a paused element and simply never fires again once the browser suspends it, so the tiler canvas freezes on its last frame even though `play()` succeeded; `bg_frame_in_flight` can also be left set. `restart_bg_video_frames()` is the whole cure (cancel + re-queue the rVFC, clear the in-flight flag, reset `bg_last_forward_time` and re-`forward_bg_time()` so the worker re-checks its buffer at the real position), and `update_bg_video()` fires it off the `bg_video_running` edge — `type == "default" && bg_video_visible` going false→true — so it covers the tab coming back AND the background switching back from `youtube`/`video`/`none`, which pause the identical element through the identical code. It hung off `set_bg_video_visible(true)` alone until 2026-08, which is why a long stay on YouTube came back to a frozen canvas. Do not move it back to a caller: the type transitions have no single choke point the way visibility does

## Non-obvious
- `state.camera.proj`/`view` are mutable `Float32Array(16)` owned by `state.js`. `prepare_3d_view()` writes IN PLACE via `mat4.perspective(proj, …)` / `mat4.view(view, …)` — never replaces the references; lower-level draw helpers only read them
- Three shared `DYNAMIC_DRAW` VBOs: `disc_vbo` (target/core fills), `ring_vbo` (target + impact rings), `guide_vbo` (aim guides; grows on demand), plus static ones built once at load: the unit sphere for `flick_180`'s camera-crossing transition and the two sky-sphere grid meshes (`sky_sphere` / `sky_sphere_major`). The sphere shader derives its yellow pixel-width silhouette from the view-space normal, so it needs no per-frame ring geometry. `build_disc_vbo_from_angles` / `build_ring_vbo_from_angles` write into module-scope `Float32Array` scratch, `bufferSubData` the shared VBO, and return the SAME `VboInfo` every call — never `deleteBuffer`, and finish the `draw_fill`/`draw_stroke` before the next `build_*` of the same kind (disc→draw→ring→draw is safe; disc→disc loses the first's data)
- Unit-circle `cos`/`sin` for disc/ring layout are precomputed once into module-scope LUTs (`unit_cos`/`unit_sin`, length `VERTEX + 1`)
- `resize_2d()` sets BOTH `canvas_el.width/height` AND `state.camera.width/height` from `innerWidth/innerHeight * devicePixelRatio`. `resize_3d()` then sets `#canvas-3d` size + GL viewport from those — it does NOT touch `sens` (it used to call `calc_camera_sens` itself; that line is gone). Order is load-bearing: `resize_2d` → `logic.update_camera_projection()` → `resize_3d`, the projection half NEVER the full `update_camera_view()` (root `CLAUDE.md:Camera derivation`)
- `convert_camera_to_2d/3d()` only transform `x`/`y` ↔ `pitch`/`yaw` — they do NOT touch `dimension`. Modes call `update_camera_view()` first, then convert, guarded by `if (x || y)` / `if (pitch || yaw)`
- `convert_target_to_2d(t3d)` handles yaw wraparound at PI (otherwise the post-conversion sign flip teleports the target across the screen)
- Both target conversions DELIBERATELY drop the core's lateral rotation (only `h_tracking` rotates its core toward movement) and rebuild it straight: 2D `cy = y - r + cr`, 3D `cp = p + r - cr`. So `convert_target_to_2d` reads `target.y`/`p` but not `cy`, and `convert_target_to_3d` reads `target.x`/`y` but not `cx`. A flip mid-rotation snaps the core upright — intentional. Both take a REQUIRED `out` as 2nd arg and write in place (returning `out`) — no internal allocation; modes pass a persistent/pooled target
- **`calc_camera_sens()` has TWO per-game escapes from "sens follows the current view's fov"**, both inside it so it stays the single producer of `sens`. Same shape — *ignore `fov_deg`, lock to the game's HIPFIRE fov rebased to the real aspect* — because neither game zoom-corrects sens. Each inlines what `calc_real_hfov(fov.<game>.axis, hipfire, width, height)` would return, so card and feel can't drift, **but the axis rule IS duplicated here — a rule change must land in both places** (`calc/CLAUDE.md`):
  - `sa` — the `"43"` rule, `max` included: `convert_deg_across_aspect(constants.fov.sa.hipfire, 4 / 3, max(4 / 3, width / height))`, matching `calc_sens_sa`. Its TRG stage multiplier comes from `sens_scale`, NOT from here
  - `bdo` — the `"v"` rule on its hipfire 70° vfov (`convert_deg_across_aspect(constants.fov.bdo.hipfire, height, width)`, matching `calc_sens_bdo`). Black Desert applies NO zoom-sens correction and exposes no separate first-person sens, so its RMB fpp view narrows to 40° while yaw-per-count stays the hipfire value. Deliberately "wrong" against the per-view-fov convention — it is what the game does. Consequence: targets/impacts spawned in that view keep hipfire ANGULAR size so they render bigger on the 40° screen, and counts-to-cross stay identical across the flip
- **`state.camera.sens_scale` is everything that makes the REAL game's yaw-per-count differ from the ideal, and only `logic.update_camera_view()` may write it.** Two factors: SA's forced TRG multipliers (`x5_sens` `.25` / `x15_sens` `.15`) and `calc_sens_snap()` (card rounding, ≠ 1 for nearly every game). The snap is VIEW-DEPENDENT — `update_camera_view()` hands it `mb_right`, so the ADS snap differs from the hipfire one (`cs2` −0.090 % → −0.171 %, `rb` −0.424 % → +0.305 %). **Do NOT compute it from `state.input.mb_right` inside `camera.js`**: `aim_booster`/`writing` have no `update_dimension`, so RMB flips `mb_right` without re-running `update_camera_view()`, and a resize would then scale `sens` to a scope the view is not in
- `px_to_rad`/`rad_to_px` read the cached `state.camera.sens` and never recompute it. They ALSO multiply by `1 + state.camera.dist / sky_sphere_radius`: the TPP orbit compresses apparent size by the inverse, so screen-px quantities (target radii, spacings, speeds, 1 px stroke, `impact.rad_size`) spawn at the SAME apparent size in fpp and tpp (`dist = 0` elsewhere ⇒ factor 1). Deliberately spawn-time ONLY — a target spawned in one view and then seen through an RMB tpp↔fpp flip is NOT re-converted, so it visibly grows/shrinks (mirrors zooming in the real game); hit tests stay consistent because pivot-space offset and radius compress by the same factor
- **Sizes go through that same `sens` map, NOT the projection's true center slope `2*tan(vfov/2)/height` — by design, not an approximation to fix.** Since the mouse is `yaw += movementX * sens`, `r = base_radius * sens` makes the mouse counts to cross a target identical in EVERY game, fov, hipfire or ADS, 2D or 3D. Rebuilding sizes on the exact inverse projection (`atan(px * 2*tan(vfov/2)/height)`) pins on-screen size at N px instead and spreads that count from 20 to 31.7 across the game list (worst: `lol`/`mc` at vfov 110) — tried and reverted 2026-07. Cost: on-screen size varies with fov (a 20 px 2D target renders 12.6 px at vfov 110, 20.0 px at a vfov-30 scope, grows on ADS) — exactly what fov does in a real game. Sub-pixel targets at extreme fov are likewise correct (at fov 179 one center pixel spans ~5°)
- Impact fade/expiry runs on `state.timer.now_ms`. `max_life_ms = duration_ms * (1 + spacing * (rings - 1))` = 210 ms is the exact point the LAST ring finishes (`ring_progress = progress - k * spacing`, drawn while `≤ 1`), so nothing is dropped while still visible. The pre-2026-08 bound added a dimensionless `spacing` to a seconds value and retained 550 ms — 2.6× longer than anything could be drawn
- Impacts are pooled: `record_shot_2d`/`record_shot_3d` `obtain()` from `impacts_pool`/`impacts_3d_pool`, fill ALL fields (`c = void 0` for a miss, so `c == null` still renders black), push. `draw_impacts()`/`draw_impacts_3d()` `recycle()` each expired entry before `drop()`. Never push a raw literal — it breaks steady-state reuse
- `draw_crosshair()` draws ONLY the crosshair. It used to also paint SA 4:3 side-crop bars with a matching `calc_camera_sens()` branch (removed 2026-08 on request) — do not reintroduce a letterbox without restoring both halves, or the bars and the sens box drift apart
- `update_crosshair()` closes the old `crosshair_image` ImageBitmap, rebuilds it, redraws the settings preview — call it on ANY `state.crosshair.*` change

## Draw orders
- **2D**: `draw_grid()` → mode `draw_target(target, alpha)` → `draw_impacts()` → `draw_crosshair()`. Modes wrap with `context_2d.save/restore` + `translate(round(w/2), round(h/2))` to center the origin
- **3D**: `prepare_3d_view()` (MUST precede any `draw_*_3d`) → `draw_grid_3d()` → mode `draw_target_3d(target_3d, alpha)` → `draw_impacts_3d()` → then `draw_crosshair()` on the 2D canvas. `Target3D` uses spherical `y`/`p`; the 3D impact radius comes from `state.impact.rad_size`

## When you change…
- 2D target visuals: `renderer_2d.js:draw_target()` + `constants.target` · 3D: `renderer_3d.js`
- Resize: `renderer_2d.js:resize_2d()` · `renderer_3d.js:resize_3d()` · `controller/window.js:on_resize()` (keep `update_camera_projection()` in the middle)
- Crosshair: `renderer_2d.js:draw_crosshair()` + `update_crosshair()`
- Impact entry shape: `record_shot_2d()` + `record_shot_3d()` + the matching pool factory in `state.js` + the `draw_impacts*` recycle/drop loop
